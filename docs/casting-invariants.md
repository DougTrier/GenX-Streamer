# Casting invariants and reuse audit

> Public copy. Evidence paths (`artifacts/...`) and linked internal reports are kept in the project's private archive; the measurements and decisions are summarised here.

Reviewed October 10, 2026. Chromecast and DLNA are required casting transports. This extends the existing 22 playback/catalog/sharing/release invariants; it does not replace them. Protocol fixture tests establish control behavior, not physical receiver playback.

## Previous project evidence

The owner confirms that the previous app was tested and casts successfully to their TV. Read-only review of `the previous app's source, app.py`, lines 19–81, 189–223 and 522–614, plus `requirements.txt`, establishes its compatibility baseline: eight-second PyChromecast discovery, a known-address fallback, and a PC-hosted HTTP stream relay. Private `tv_config.json` was not opened. Preserve these capabilities with explicit receiver selection and scoped relay resources. The detailed comparison and upstream failure/fix evidence are in the compatibility audit.

The previous implementation automatically picks the first sorted device, uses a hardcoded fallback address, reports casting after activation rather than confirmed media progress, and returns stop success without observing receiver state. Discovery cleanup is outside `finally`; sender sockets/session state are not disposed/reset after stopping. The relay decodes arbitrary target URLs. `pychromecast` is imported but absent from declared requirements. These are source observations, not measured hardware failures. Household addresses and personal settings must not become product defaults.

## Primary research and limits

Home/hotel/conference selection, venue pairing, network isolation, polling hazards and recycled addresses are covered by [travel casting research](travel-casting.md). Its prevention rules extend these existing contracts; no new numbered invariant or universal receiver guarantee is introduced. T100 tracks implementation and fault/physical acceptance.

- Google documents receiver-dependent codec support, HLS support, mandatory CORS for adaptive streams and additional receiver work for DRM. Sender playback cannot establish receiver compatibility. [Supported media](https://developers.google.com/cast/docs/media), [receiver/CORS documentation](https://developers.google.com/cast/docs/web_receiver/basic).
- PyChromecast issue 1247 reports an indefinitely stalled launch on Nest Audio. It remains open; this is a reported failure, not a confirmed fixed defect. Own operation deadlines independently of library waits. [Issue 1247](https://github.com/home-assistant-libs/pychromecast/issues/1247).
- Issue 738 documents Audible session interference and closes through PR 886. Current upstream socket code contains a one-second Audible channel connection workaround. This confirms an upstream compatibility workaround, not a general timing fix for IPTV. Do not copy arbitrary sleeps or take over unrelated receiver apps. [Issue 738](https://github.com/home-assistant-libs/pychromecast/issues/738), [current socket implementation](https://github.com/home-assistant-libs/pychromecast/blob/master/pychromecast/socket_client.py).
- UPnP AVTransport defines URI loading, Play, Stop and transport state queries. A successful SOAP action is not proof the renderer consumed playable media. [AVTransport specification](https://upnp.org/specs/av/UPnP-av-AVTransport-v3-Service.pdf).
- The async-upnp-client changelog records polling when subscriptions are rejected (0.22.11), handling bad optional Get actions (0.30.0), IPv6 Host header correction (0.30.1) and IPv4/IPv6 discovery deduplication (0.25.0). These are documented fixes, not verification of our adapter. Preserve optional-action tolerance while requiring actual playing/stop evidence. [Upstream changelog](https://github.com/StevenLooman/async_upnp_client/blob/development/CHANGES.rst).

## Mandatory casting contracts

| ID | Invariant | Required verification |
| --- | --- | --- |
| C01 | One casting session owns its sender connection, receiver transport identifiers, timers, subscriptions and cleanup. | Rapid device/channel switches; failure during allocation/disposal. A replacement starts only after the previous session has been asked to stop and released (see C05). |
| C02 | Stale callbacks cannot publish status or control a replacement session. | Delay receiver launch/load/status/stop replies; require application generation, sender session, selected channel and remote media session ownership. |
| C03 | Receiver fetch and receiver state determine success. | Sender LOAD acceptance stays Connecting; require matching receiver PLAYING status. Test unreachable media host, CORS, receiver DNS, and codec faults; record physical receiver identity. |
| C04 | Casting preserves access restrictions. | Test provider authentication, geo restrictions, unsupported DRM and expired URLs. Do not forward cookies/secrets indiscriminately or promise restriction bypass. |
| C05 | Stop controls the owned receiver media, revokes the relay, and waits up to five seconds for the receiver to confirm before releasing sender resources. | Disconnect differs from Stop. Test refused stop, lost receiver, app takeover, stale media IDs and shutdown. A receiver that does not confirm is released anyway and never blocks casting to another TV (owner decision, October 24, 2026); the viewer is told it did not answer. |
| C06 | Receiver URLs and discovered control endpoints have distinct, explicit network policies. | Public media destinations validated on every redirect. Native discovered private LAN device endpoints are restricted to validated discovery records; never expose arbitrary URL relay. Receiver-specific relay grants have bounded lifetime and no user/provider credentials. |
| C07 | Compatibility and retries are bounded and contextual. | 20-second launch/play confirmation episode, 5-second stop deadline, no indefinite library wait. No automatic repeated LOAD after ambiguous acceptance; user retry after cleanup. Exercise vendor SOAP differences and media MIME/profile matching. |
| C08 | Discovery occurs only on explicit user action and releases sockets. | 10-second bounded discovery, device deduplication, cancellation, shutdown, multi-interface/IPv6 and malformed XML/SSDP. No hardcoded household addresses, auto-first-device selection, background permanent scanner or automatic firewall exceptions. |

## Adapter boundary

`src/casting/controller.ts` takes an injected adapter; its unit tests use controlled engines. `listDevices` is the explicit discovery call. `start(device, selection)` creates a session-bound adapter; event envelopes carry session and selection IDs. PLAYING requires a receiver session ID. `stop` asks the owned receiver to stop (five seconds at most), then disposes the sender and releases the session whether or not the receiver confirmed; switching TVs does the same for the previous one first. Diagnostics are user messages, not raw provider/control payloads.

Windows candidate: native mDNS `_googlecast._tcp.local.` and Cast V2 connection/media channels; DLNA SSDP discovery followed by XML AVTransport service descriptions and bounded SOAP requests. Android should prefer official Google Cast SDK integration where practical; a shared native protocol implementation remains a candidate until device/network proof. Native discovery and physical Chromecast/DLNA testing are outstanding acceptance evidence.

The native candidate now resides in `src-tauri/src/sharing/casting/`: eight-second repeated mDNS discovery on eligible private IPv4 interfaces, missing-record follow-ups, partial failure warnings, SSDP discovery bound to sender IP, AVTransport XML/SOAP, Cast V2 protobuf framing, TLS control messages, heartbeat replies and owned media status/Stop. Frontend `createNativeCastAdapter` uses inspected content/MIME rather than URL extensions and polls status only while a session is active. The collapsed known-receiver form probes a user-entered private IP with CONNECT/GET_STATUS; it never launches media. Casting starts through a separate receiver-selection action. Closing the dialog suppresses late probe results; native probe resources expire within bounded deadlines. No address is hardcoded or automatically selected.

The working old app always relays media through the PC. Preserve that path as a separate receiver-scoped capability with opaque URLs and route-derived interface selection. Receiver HTTP consent is now implicit in choosing the TV (owner decision, October 19, 2026: "Press Cast => Select TV => it plays on TV"). Before loading, GenX makes one small ranged request with the receiver's origin; when the stream is plain HTTP or its actual response lacks a cross-origin grant (SportsGrid grants it only to the preflight, and the TV then shows only its blue cast icon), GenX relays it automatically. Trade-off: a relayed stream travels unencrypted on the local network, as in the old app. The relay stays receiver-scoped, short-lived and separate from encrypted browser/phone sharing; it refuses non-public upstreams, so Paid TV's local playback proxy cannot be cast yet. A failed load closes the TV's receiver app, because the TV's Back button cannot leave it. Measured on the Streamer the same night: (1) its mDNS responder ignores a question sent straight to it but answers the same question sent to the mDNS group, with the reply coming from the TV to GenX's socket, so the identity recheck now asks both ways and still reads only the selected TV's answer (no acknowledgment step for a verified TV); (2) right after LOAD the Default Media Receiver reports an empty or idle status before its player starts, so a load fails only on LOAD_FAILED or idle with a reason; (3) after Stop it reports the ending playback once before going idle, so Stop waits for idle (five seconds at most) and then closes the cast app GenX launched, never one where another sender's media plays; (4) the start limits are 40 s native and 45 s in the page, because launching the cast app and buffering a relayed live stream took about 11 s. Relay implementation and physical compatibility remain open; direct provider casting alone does not establish equivalence with the old app.

Remaining gates: IPv6 multicast and scoped link-local discovery; Google Cast device-authentication attestation (the local receiver TLS verifier checks handshake signatures but does not establish Google device identity); secure receiver relay grants that validate upstream redirects and playlist segments; DLNA same-URI external takeover ambiguity; receiver MIME/vendor compatibility; physical receiver startup, progress, stop and app-shutdown tests on both supported platforms. Direct public URL casting cannot independently verify redirects fetched by the receiver. A window-destroyed cleanup task alone cannot prove remote Stop completed before application exit.

## Implementation verification

Additional October 10 compatibility work: `npm run typecheck` and `npx vitest run tests/casting/known-receiver.test.ts tests/casting/native-adapter.test.ts` passed (nine assertions across two files). Probe tests prove no media command is sent, browser preview declines the operation, and a cancelled owner suppresses a late result. `npx playwright test tests/ui/source-management.spec.ts` passed all seven tests, including the collapsed manual-receiver entry and truthful browser-preview status. Native private-IP and CONNECT/GET_STATUS-only policy fixtures are separate from these command mocks. The native integration reports 50 tests and clippy passed; packaged and physical receiver proof remain separate. Build `index-DUg5MTwY.js` includes this UI, with its deferred HLS dependency still above the bundler's 500 KiB advisory threshold.

October 10, 2026, Windows x86_64, Rust 1.96.0. Static deterministic fixtures (no random fixture seed). Neither discovery nor casting was run against a household device.

- `npx vitest run tests/casting`: exit 0, 15 tests passed. Includes isolated controller ownership, late status, bounded startup timeout, failed/unconfirmed stop, explicit discovery, disposal, bridge cancellation and content/MIME selection. Native command mocks are explicitly labeled.
- `npx eslint src/casting tests/casting`: exit 0.
- `npm run typecheck`: exit 0 after frontend adapter integration.
- `cargo test --offline --manifest-path src-tauri/Cargo.toml casting`: exit 0, 15 casting tests passed. Includes actual loopback HTTP/SOAP load/status/owned stop and refusal to stop a foreign URI; real mDNS record decoding; protobuf frames, XML entities/DTD/depth and public-media/private-device boundary. Loopback is confined to internal transport fixtures; production discovered endpoints refuse loopback.
- `cargo clippy --offline --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`: exit 0.

The independent `src-tauri/src/sharing/casting/verify/Cargo.toml` harness builds the same modules when a platform build is occupied. It is a protocol fixture aid, not a replacement release build or hardware test. `npm run verify` builds it and runs its tests (the `casting-harness` step).

Reuse is architectural rather than copying the older Python server into a portable application. Pins, protocol tests, receiver reachability and shutdown evidence are required before claiming transport support.
