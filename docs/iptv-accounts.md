# IPTV accounts and device vaults

> Public copy. Evidence paths (`artifacts/...`) and linked internal reports are kept in the project's private archive; the measurements and decisions are summarised here.

October 14, 2026. Requested capability for future users, researched design and acceptance plan; **partially implemented, not accepted**. The native device vault and metadata commands exist; authenticated acquisition, opaque media integration and usable account entry are still being assembled. The user has no subscription credentials. Both formats are required: Xtream-compatible server URL plus username/password, and provider-issued authenticated playlist/token URLs. No real account details were requested, downloaded, logged or tested; no paid account or old private configuration was used.

## Status update, October 16, 2026

Since the text below was written, a real one-connection trial account (Xtream login and its `get.php` playlist link) has been signed in by the user and used on the Windows desktop build. Superseded statements below are kept for history; current behaviour:

- **HTTP providers:** a separate, per-account HTTP permission now exists (the user ticks it when adding the account). The stored origin still pins scheme, host and port, and HTTPS never downgrades. The public-source HTTP checkbox still grants nothing to accounts.
- **Live TV:** both account kinds acquire and play (MPEG-TS through mpegts.js, HLS through hls.js) via the loopback relay; the browser never receives a credential.
- **VOD:** movies and series are browsable (Paid TV → Video On Demand). Playback is wired through the same relay, but the trial provider refuses movie files; see provider compatibility.
- **Location:** paid channel groups resolve to the app's country codes (`group_country`); the Paid TV list filters and sorts by country, and unresolved groups stay listed under All countries and Unknown.
- **Viewing choices:** Settings → Hide adult channels (on by default; one choice for Free TV, Paid TV and Paid TV VOD categories) and a per-account live buffer (Fast start / Balanced / Extra smooth), stored natively beside the account data. Adult channels were visible by default before this change.
- A01–A08 are still **not** accepted; Android TV account entry and playback have not been verified on this build.
- **Provider redirects (October 18, 2026, owner decision):** channel import now follows a provider's redirect to another public server, as playback already did. A trial's front door (`smartdns.eu.cc`) answered every endpoint (`player_api.php`, `get.php`, `xmltv.php`) with a 302 to its real server (`cf.onvpn.eu.cc`), carrying the sign-in in the provider's own Location; import refused it (`account-redirect-refused`) and the account showed no channels on the Google TV Streamer. Rule, shared with `account_playback_proxy::redirect_target`: GenX adds nothing to the address it is given, at most 5 hops, every hop's DNS answer must be public (no private/loopback/user-info addresses), and an HTTPS account is never downgraded to HTTP. This supersedes "never forward credentials to an unrelated redirect origin automatically" below for provider-issued redirects.

## Present boundary

The native `account_vault` and `account_vault_owner` modules store whole account secrets in OS-protected device files, keep only metadata in SQLite, fence updates by account revision and storage generation, and revoke references on removal. Android requests the actual application `noBackupFilesDir`; Windows uses the application local-data directory. `list_iptv_accounts`, `save_iptv_account`, and `remove_iptv_account` expose metadata and committed receipts only. There is no frontend secret-resolution command. Account transport is HTTPS-only; the public-source HTTP checkbox does not grant an exception.

`account_acquisition` acquires Xtream-compatible live catalogs and authenticated playlists entirely in native code, with public DNS pinning, same-origin HTTPS redirects, fixed errors and a shared twenty-second/20 MiB budget. `inspect_iptv_account` returns counts and availability, explicitly without decoder proof. `refresh_iptv_account` installs the result through `account_media_store`: secret URLs occupy bounded OS-protected device pages, while SQLite holds stable channel metadata and opaque stream references. Account, storage and media revision fences guard atomic replacement. Cleanup after committed publication is advisory and cannot change a successful write into a reported cancellation. Paid TV guides (October 18, 2026): `refresh_iptv_account_guide` downloads the provider's own guide only when the viewer opens the Paid TV Guide (or presses Update guide), at most every 12 hours otherwise. Xtream accounts use `xmltv.php`; playlist accounts use the playlist header's `x-tvg-url`/`url-tvg` on the account's own server. The address is built natively and never leaves native code. The download streams through the account fetch policy (public DNS pinning, provider redirects, 256 MiB cap) into an app-cache temporary file that is always deleted; gzip is recognized by its bytes and bounded at 768 MiB expanded. The streaming reader keeps XML structure strict but skips unusable listings (counted). Listings bind to channels only by the provider's exact EPG ID (XC-034), within six hours ago to eight days ahead, at most 600,000 per account. `account_guide_v1`/`account_guide_program_v1` are replaced in one transaction for the downloaded account revision; a failed, canceled or stale download keeps the last good guide (XC-036), an edited account hides it, and removal cascades it away. A separate EPG link field for playlist accounts, Xtream short EPG and Base64 titles (XC-031/032) remain open.

Shared metadata/inspection bridges and the inline account form are implemented, and the form is now mounted in Sources settings. Saved accounts populate a channel-library selector, and native account queries feed the existing virtualized channel list and player. Watch channels opens that library; account selection stops public sharing before playback. Resume/Retry reacquire local capabilities, while account favorites, location data and guides remain unfinished. The existing public-source `Channel.urls` schema must not be filled with credential-bearing URLs or fabricated public addresses. Native account media resolution and the loopback playback proxy are wired: revision-fenced native resolution feeds a singleton transport with opaque session/resource URLs, constrained HTTPS upstream requests and joined shutdown. Shared playback startup compensates late cancellation through exact-generation Stop. The browser engine now accepts an optional session request boundary, checked initially and on every native HLS request. The shared coordinator and UI now use that boundary; runtime decoding and failure-path acceptance remain unverified. Windows/Android decoder proof, account-aware export/restore and guide integration remain open. These are implementation facts, not A01–A08 acceptance. Compilation receipts are under `artifacts/account-cast-import-integration`; physical vault, portability, backup, cancellation and playback proofs remain outstanding.

Current sources accept public HTTP(S) playlists with explicit HTTP permission. `src/catalog/parser.ts`, `src/catalog/codec.ts` and `src-tauri/src/discovery/network.rs` reject URL userinfo, but do not classify every secret embedded in query parameters or URL paths. Catalog/preferences and the ordinary backup codec preserve source/stream URL strings. **A token-bearing URL entered through today's ordinary source flow is not automatically vaulted.** Do not describe existing account links as protected by the proposed vault.

Account support requires an account-aware source/stream reference and native credential resolution before it can be enabled. Hiding a password field, masking a label or encrypting just the password while persisting the credential-bearing URL would not satisfy this design.

## Supported formats and scope

| Format | Planned entry | Native adapter boundary |
| --- | --- | --- |
| Xtream-compatible Live TV | Display name, provider's server address, username, password | Authenticate; admit bounded live catalog/categories and supplied guide data; construct requests only inside the native account owner. Preserve stable account/stream IDs across refresh. |
| Authenticated playlist/token URL | Display name and the entire provider-issued URL; optional separately supplied authentication method only when implemented | Treat the **whole URL** as secret. Store it in the device vault; acquire/parse a bounded playlist, then retain opaque stream references rather than plaintext secret URLs in the catalog. |

[XUI.live's implementer documentation](https://xui.live/docs/api/xtream/) describes a Xtream-compatible player API, Live TV catalog actions, short/full guide actions and playlist/XMLTV endpoints. It also shows authentication in query parameters and playback credentials in URL paths. This is primary documentation of one implementation of a de facto protocol, not proof every service follows it. Confirm provider-specific pagination, expiration, guide IDs, connection limits and response formats using controlled fixtures and an explicitly authorized service. An account result or a listed channel is not decoder evidence.

Provider metadata cannot authorize arbitrary new destinations. Retain the existing public-DNS/redirect/scheme/content/deadline limits; validate returned URLs and never forward credentials to an unrelated redirect origin automatically. Support Live TV first. VOD, catch-up, series, MAC/portal emulation and administrator/reseller APIs are not silently included in this account task. An authorized subscription does not establish casting or retransmission rights.

## Native device vault

The proposed native `SecretStore` contract is `put/update/delete/resolve`, keyed by random opaque account ID and app namespace. Resolve is internal to native acquisition/playback; there is no general frontend read-password API. SQLite and preferences contain display metadata, transport kind, non-secret endpoint metadata where safe, and vault references. Never copy passwords, bearer tokens, credential-bearing source/stream URLs or their reversible encodings into catalog/health records, ordinary backups, logs, debug receipts, screenshots, command lines or browser storage. UI entry holds secrets only transiently and clears fields after admission/cancellation; do not promise complete process-memory erasure.

**Windows:** Microsoft recommends [Credential Manager or DPAPI for stored secrets](https://learn.microsoft.com/en-us/windows/win32/secbp/handling-passwords). A generic [Credential Manager entry](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw) with local-machine persistence remains scoped to the same user's logon sessions on that computer; its documented secret blob maximum is 2,560 bytes. That cannot represent every allowed long authenticated URL. Proposed initial adapter: a bounded, versioned atomic vault file protected by **current-user DPAPI**, separate from SQLite. Avoid machine-wide DPAPI scope or embedded encryption keys. [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) ordinarily requires the same logon identity and computer, with documented exceptions. A copied portable app/catalog is therefore not a portable login; prompt for re-entry when the destination vault cannot resolve it. Neither mechanism protects against every process already acting as that user.

**Android/Google TV:** generate an app-scoped AES-GCM key through Android Keystore and atomically store authenticated ciphertext with fresh nonces in app-private no-backup storage. Keystore protects cryptographic keys; it does not directly store arbitrary password strings. Hardware backing depends on the device and algorithm; inspect capability rather than claiming StrongBox on every TV. Key operations must run off the viewing thread. These constraints follow [Android Keystore documentation](https://developer.android.com/privacy-and-security/keystore). Missing/invalidated keys, cleared app data or unsupported vault operations must require re-entry, never plaintext fallback. TV devices may lack a lock screen, so requiring biometric/device-authenticated key use needs a separate usable design rather than an unconditional requirement.

Exclude device-vault material from cloud and device-transfer backups using the applicable rules and no-backup directory; test the actual packaged manifest. [Android backup documentation](https://developer.android.com/identity/data/autobackup) distinguishes backup/transfer modes and excludes no-backup files. Current manifest has no demonstrated account-vault backup exclusions because this feature is not present. Ordinary GenX exports may carry account metadata and missing-vault references only, clearly marked **Sign in again on this device**. An independently designed encrypted credential-transfer feature is not part of the initial plan.

## Transport and lifecycle

Credentialed login, playlist, guide and playback acquisition must use validated HTTPS in the initial secure account adapter. Native code may have to put credentials in an ephemeral request URL because of the service protocol; that address must never become a persisted catalog URL, frontend media URL or diagnostic. TLS prevents passive transport disclosure, but cannot prevent the provider from seeing or logging its own requests. Never silently downgrade HTTPS, bypass certificate validation or guess an alternative provider port.

The existing public-source HTTP checkbox does **not** authorize sending account credentials over plaintext HTTP. If the user later requests compatibility with an HTTP-only provider, it requires a distinct, scoped informed choice and its own policy/tests; vault encryption does not make that network transport secure. [Android's network security configuration](https://developer.android.com/privacy-and-security/security-config) has API-dependent cleartext defaults and explicit opt-in mechanisms. Its manifest/platform setting is separate from this app's per-request native policy; changing it is not account TLS validation.

Keep one playback owner and bounded account acquisition. Respect account connection limits without a second decoder or continuous probing. Background/exit/account removal cancels and joins pending jobs; generation/revision fences prevent a late login/refresh from recreating a removed account. Account updates publish references only after vault success, preserving the previous usable account on failure; crash recovery must reconcile orphaned ciphertext/references without revealing secrets. Deleting the local account does not revoke the provider subscription. CAST/LAN routes remain unavailable for credentialed media until their own scoped, encrypted native resolution and authorization are proven; do not hand a receiver the login URL.

## Reported failures and verified fix status

Primary project reports reviewed October 11, 2026. A reporter's observation is a regression lead, not proof every provider or platform fails. Closed issues and merged changes are distinguished from fixes reported without successful retesting. These findings inform planned A05–A07 cases; they do not establish GenX account support.

| Primary report | Observed status and lesson | Planned controlled regression |
| --- | --- | --- |
| [IPTVnator #571](https://github.com/4gray/iptvnator/issues/571) | Closed as completed September 23, 2026. The report describes a custom server port becoming port 80; the maintainer identifies v0.22.0/#1065 as preserving the server port in stream URLs. This is maintainer-confirmed fix status, not an independently tested service. | Preserve scheme, explicit port and supported base path through authentication, catalog and media URL construction. Fixtures include HTTPS on port 8443, escaped credential characters and two accounts on the same host. Never guess a port. |
| [IPTVnator #1400](https://github.com/4gray/iptvnator/issues/1400), [merged fix #1404](https://github.com/4gray/iptvnator/pull/1404) | PR merged August 10, 2026. Its documented Node backend fix raises address-attempt time, retains IPv6/IPv4 fallback and exposes safe transport error codes instead of an unexplained 502; tests cover credential-free diagnostics. That runtime-specific setting is not a Rust implementation recipe. | Unreachable IPv6 with reachable IPv4 completes under a bounded whole-operation deadline; network failures are not mislabeled invalid passwords. Keep existing destination validation/DNS pinning. Redact full requests and credentials from all error paths. |
| [Kodi PVR IPTV Simple #715](https://github.com/kodi-pvr/pvr.iptvsimple/issues/715) | Open. Reporter narrowed a Basic Auth failure to redirect/challenge ordering; direct HTTPS reportedly worked. Contributors could not reproduce across their tested Kodi environments. No verified linked fix was established. | Controlled GET/redirect/401 ordering, authenticated playlist acquisition and cache/HEAD differences. Send authentication only to an authorized origin; refuse unrelated redirects and downgrade. A vault-backed Basic Auth adapter must not rely on persistently embedding userinfo. |
| [IPTVnator #1144](https://github.com/4gray/iptvnator/issues/1144) | Open, more information requested. A new Xtream entry was rejected while an older saved entry worked. After a maintainer's later-version guidance, the reporter still described failure and inability to add another account. Do not mark this resolved on a release claim alone. | Fresh and migrated entries, multiple distinct accounts and actionable address-format errors. Adding/removing one account preserves others and their stable references; failed validation never replaces a usable saved account. |

Use simulated HTTPS Xtream/playlist services and generated test-only secrets to reproduce these cases without a real subscription. Native vault/platform proofs remain separately required. Do not adopt another project's insecure TLS bypass, provider URLs, credential logs or unbounded retry merely because it appeared to work.

No endpoint, login, signing key or security exception is introduced by this document.
