Current flow is: approved descriptor → bounded native acquisition → offline expansion/parse → owned preview → validated atomic cache publication → exact current-catalog connection → bounded local query → safe UI text. Cache publication can occur without changing mappings; cached connection is a separate catalog/source/published-revision fenced transaction. Each acknowledged channel scan batch requests the same coalesced foreground guide builder. It does not create a download per channel.

## Current bounds and their meaning

The native input limit is 20 MiB, expanded XML 64 MiB, channels 100,000 and programs 500,000 per feed. Gzip magic admits at most two layers, including concatenated members; overflow or corrupt compression refuses the complete new feed. These are admission caps, not evidence that four concurrent maximum-size feeds fit a TV heap. Native guide active work is capped at four; normal automatic acquisition is sequential. Source/provider descriptors are independently bounded to 100. Category metadata admits at most 32 raw elements/program, 512 UTF-8 bytes each and 4096 aggregate bytes.

Selected summary replies cap at 128 KiB. Visible summary requests admit 1–64 exact channel pairs and cap the whole envelope at 512 KiB; no truncation. Program/channel pages, cursors and adapters have separate caps. These boundaries preserve whole-result refusal and actual cancellation joins. Future streaming or subset parsing must preserve complete source channel validation, program reference checks, overlap truth and transactional publication; discarding unmatched rows cannot silently claim a complete imported feed.

## Matching and pinned user intent

An existing explicit mapping remains authoritative. Automatic connection may fill previously unconnected channels using exact IDs or compiled verified aliases, but must not overwrite an explicit mapping because a newer or higher-scored feed appears. The mission's hierarchy is a candidate search order, not permission to demote confirmed user choice. Normalize names with qualifiers/country/time-shift distinctions retained; fuzzy matches, aliases without verified provenance and regional guesses require confirmation. A stream URL or display name is never universal identity.

The present mapping records contain one selected guide source/channel per catalog identity, without a persistent “manual versus automatic” provenance/pin field. A source-ranking/fallback implementation therefore needs explicit mapping-origin/pinned-choice metadata or an equally strict non-overwrite protocol before changing selections. Preserve current source-scoped IDs, reviewed alias authority, variants, favorites, removals and category overrides. No XML rewriting is required.

## Coverage and fallback design to implement

Assess a cache using source/config/published revisions, real last-success time, bounded clock tolerance, nonempty admitted programs and actual schedule instants. Timestamp assessment should label expired, future-only, unknown-end and incomplete coverage separately; a recent download of yesterday's listings is not fresh coverage. Source-wide min/max is only a coarse diagnostic. Per-channel interval analysis must report gaps/overlaps and requested horizon coverage, with a bounded query/result design.

The first safe improvement is a pure coverage assessment using existing `listSources` and `coverage` replies, tested with injected clocks. Next add conditional-request metadata bound to the exact source definition and last-good revision. A 304 may reuse only that validated cache and must reassess its temporal coverage; it cannot turn expired data into a successful seven-day update. Persist actual last attempt and successful publication separately. Retry-After, failure backoff and source health need bounded, redacted storage, not speculative client loops.

Fallback should retain the primary cached schedule until a validated alternate for the exact channel is eligible. Rank candidates by measured matching coverage, known future intervals, freshness, reliability, response/resource cost and permitted use. Never select an alternate by global feed program count alone. Keep pinned choices; ambiguous candidates remain available for user review. Failed/empty/canceled candidates cannot remove the working schedule. No current automatic scoring or per-channel alternate selection is claimed.

## Evidence rank

1. **Implemented and fixture-proved:** native parse/gzip/time/category admission; source-scoped mapping/aliases and CAS; transactional schedule/cache connection; current/next ambiguity; bounded summaries/paging; worker and shutdown joins; foreground cadence. Exact fixture/report scope is cataloged in implementation progress and the companion EPG-TEST-REPORT.md when produced. A passing full shared or native suite is not a physical guide stress test.
2. **Historical installed scoped proof:** Windows report `artifacts/native-guide/2026-10-10T19-07-25.344Z/report.json` records exact executable, actual decoder progress, double-gzip/file guide UI, SQLite rows/mappings and cleanup. TV report `artifacts/tv-guide-route-proof/2026-10-11T23-11-06.738Z/report.json` records native Guide routing on its exact installed successor. They do not prove this working tree or all G01–G08.
3. **Known failures retained:** `artifacts/tv-ime-navigation/2026-10-11T16-41-57.263Z/report.json` failed Guide rows under scan load; future-guide V5–V12 receipts retain startup/observer/restore failures rather than being relabeled success. Scan V8 heap-limit crashes on Flip2/TV are documented in implementation progress; source memory/SQL fixes are not a full accepted feed memory proof.
4. **Still missing:** current pinned Windows/Android multi-provider refresh+navigation failure proof, maximum-input peak-memory/latency measurement, two-hour combined browsing/playback soak, corruption/storage/full lifecycle acceptance, complete provider freshness/license inventory, conditional updates and truthful per-channel fallback. Seven-day navigation remains a window, not a promise that a provider supplies seven days.

Historical EPGShare inspection at `artifacts/guide-source-inspection/2026-10-11-epgshare/report.json` illustrates why research admission differs from product admission: one parsed public feed expanded to 75,786,590 bytes, exceeding the native 64 MiB limit, with shorter observed schedules and no exact catalog IDs for the cited relevant names. Do not silently raise limits, bundle this data or treat names as verified mappings. Provider investigation and terms belong to the source registry, not engine defaults.

## Dependency order and release gates

1. Finish timestamped source registry and licensing classifications; distinguish actual data freshness from repository activity. Prefer smaller relevant feeds where verified.
2. Test pure cache temporal assessment; expose actionable source health without adding technical dashboards to viewing.
3. Add definition-bound conditional fetch and durable bounded backoff, preserving last-good/CAS/joins.
4. Measure current maximum and realistic inputs on identified hardware; implement genuine bounded streaming/staging only if required, with whole-feed safety and crash tests.
5. Add provenance/pinned-choice metadata and explicit safe candidate review before ranked channel fallback or fuzzy assistance.
6. Record exact current binaries, migrations, provider fixture hashes, decoder ownership, timestamps, latency/PSS/heap/resource counts and final cleanup for Windows and physical Android. Run sustained-abuse tests; do not estimate coverage or performance as fact.

Guide data is third-party metadata, not stream authorization. No redistribution, server aggregation or packaged feed data is approved merely by free access. Generator code and schedule-data licenses must be recorded separately. User-configured local/URL ingestion remains available within the existing privacy and destination boundary.
