# Embedded SQLite storage

> Public copy. Evidence paths (`artifacts/...`) and linked internal reports are kept in the project's private archive; the measurements and decisions are summarised here.

Decision, October 10, 2026. The owner requested SQL-backed channel storage for speed and resilience and asked whether SQLite or SQL Express fits. Choose SQLite for the private portable Windows/Android application. It runs embedded without a separate database service. SQL Server Express adds a server deployment and does not fit the shared portable device architecture. [SQLite serverless design](https://www.sqlite.org/serverless.html), [Microsoft editions](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025).

## Data and transactions

Native canonical data uses normalized sources, channels, ordered stream URLs, favorite identities, removed-channel identities and audio/layout preferences. Index source/channel identity, source membership, category and searchable names. Favorite/removal identities may reference temporarily absent channels; do not discard them or force them through a channel foreign key. Stream failures remain observations; removal is an explicit user action, retained through refresh.

One SQL transaction publishes each refresh/import or full paired replacement. Schema migrations have an explicit version and a backup before upgrade. Enforce source/channel foreign keys, use prepared statements for all user values, bound lock waits, and run storage operations outside the viewing thread. Startup integrity checks and actionable recovery preserve the previous database instead of silently overwriting it with empty data.

The initial local-file policy is rollback DELETE journaling with synchronous FULL and a two-second busy timeout, subject to actual test evidence. This avoids introducing WAL sidecar-copy obligations into portable distribution while writes are serialized. SQLite atomic transactions still rely on filesystem locking and flush behavior; no claim of impossible corruption is made. [Atomic commit](https://www.sqlite.org/atomiccommit.html), [corruption causes](https://www.sqlite.org/howtocorrupt.html), [WAL constraints](https://www.sqlite.org/wal.html).

## Portability and compatibility

Bundle a pinned SQLite implementation in Windows and Android packages; no SQL installation, service, administrator privileges, or database network port. Keep canonical data in the existing approved local user/portable directory, with the existing path/link checks. Do not operate the live database on a NAS/network share or synchronize/copy it while open; export a consistent app backup instead.

Existing new-app JSON records are read-only migration input and remain available for recovery. The previous TMG app is an explicitly selected JSON import, never an automatic read of private configuration. Full JSON backup/export remains the platform-independent interchange. Browser development uses one strict IndexedDB transaction for paired records; it is not evidence that native SQLite works.

The frontend record-pair adapter initially remains a compatibility boundary. SQLite rows are authoritative, while a reconstructed bounded catalog can feed the current virtualized browser. Native indexed query/paging requires a separate adapter and measured 100,000-channel performance; do not claim a speed improvement merely because storage moved into SQLite.

## Acceptance still required

Aggregate storage policy v1 sets a 1 GiB database page ceiling, derived from the actual SQLite page size. Guide feed transactions refuse additional occupied-page growth when total occupied database pages exceed 512 MiB, preserving capacity for channels, health observations and scan checkpoints. This is a shared database admission threshold, not a measurement of guide bytes alone. Existing above-threshold data remains intact; non-growing or reducing replacements remain permitted. Capacity refusal rolls back the entire feed transaction, including mappings and HTTP validators. Canonical record, candidate and per-feed input limits remain unchanged. These limits do not guarantee that every maximum-size source fits, nor prevent the filesystem itself from filling. Native fixtures and packaged large-scan verification are required before claiming this policy fixes the observed failure.
